# Benchmarks: RustSpice vs. ngspice-47

> Generated by `rustspice bench-ngspice` (RustSpice 0.1.0 @ 68b76cd, release build) in 127 s. Every number below was measured in this run unless it is explicitly labelled *previously published*. **Absolute numbers are valid only for the host and load recorded here; trust ratios within this run, not across runs.**

## Scope of every number

- **Host**: 13th Gen Intel(R) Core(TM) i9-13900HX (32 hardware threads). Load average 25.2 at start, 25.4 at end; sequential children pinned to CPU 11 (parallel workloads never pinned). Scratch files on tmpfs (/dev/shm). Parent peak RSS 337.9 MiB.
- **Simulators**: ngspice-47 timed with BOTH of its direct solvers: SPARSE 1.3 (its default; the old report mislabelled it KLU) and KLU (`.options klu`); the headline compares against the faster of the two per metric. RustSpice solver kind is shown per case.
- **Temperature**: 27 C (300.15 K) in both tools (RustSpice has a fixed 300.15 K).
- **Tolerances**: ngspice as-is: defaults (reltol 1e-3, vntol 1e-6 V, abstol 1e-12 A), SPARSE and KLU. RustSpice: fixed internally (the audit found `.options` ignored: reltol 1e-6, vntol 1e-10 V, abstol 1e-12 A). Reference runs: op/dc `.options reltol=1e-9 vntol=1e-12 abstol=1e-15` (SPARSE); tran `.options reltol=1e-6 abstol=1e-15 vntol=1e-9` and tmax = tstep / 20 (SPARSE).
- **Step policy**: RustSpice: fixed step equal to the `.tran` tstep (first step backward Euler, then trapezoid; no local-error control, no breakpoints), one rawfile row per step. ngspice: default adaptive step control with maximum step tstep; `ngspice -b -r` writes ITS OWN internal time points (not a uniform grid), so the row counts of the two tools differ (see the transient tables). The comparison interpolates RustSpice, ngspice and the reference linearly onto the nominal `k * tstep` grid afterwards; the ngspice error reported therefore depends on that comparison grid.
- **Timing protocol**: both contenders are subprocesses writing a rawfile (`rustspice run --raw --stats`, `ngspice -b -r`). One warm-up run (also the correctness run), then 9 interleaved repetitions in rotating order (timing enabled). A contender whose OWN warm-up takes over 1 s / 5 s is repeated at most 5 / 3 times, and heavy multi-launch workloads (each repetition already averages many launches) at most 3; a cap applies only to that contender, never to the others. Every table shows the repetitions n actually completed, and a contender that failed in any repetition never enters a headline ratio. Statistics: min, median, stddev; a series is `noisy` when stddev / median > 0.2. End-to-end = wall time of the child including start-up (the headline). Analysis-only = the tool's own analysis time: ngspice `Total analysis time` (which includes ngspice's matrix setup) and RustSpice `analysis_us`, which EXCLUDES RustSpice's symbolic analysis / JIT setup booked as `compile_us`; the analysis-only ratio is therefore not like-for-like, and the like-for-like ratio divides by RustSpice `compile_us + analysis_us`. Overhead = e2e - analysis-only. Start-up floors are measured separately below.
- **Accuracy protocol**: full waveform / full sweep / all nodes against a tightly converged ngspice reference through the engine's `compare` machinery (probes whose reference never leaves the floor are `vacuous` and excluded; the transient swing floor is 0.033 V). ngspice's own default-tolerance error against the same reference is shown next to RustSpice's, but that distance is bounded below by the reference's own error; where an independent oracle exists (exact ladder recursion, dense Newton, linear-circuit transient solution; `n/a` otherwise) it judges RustSpice, ngspice default and the reference itself, and is the accuracy figure. Never 0 for an unmeasured quantity.

## b6: batch of supply corners

The same corner values on both sides. RustSpice: rayon batch (all threads and one thread), a sequential in-process loop, and a `.dc` sweep. ngspice: sequential launches, concurrent launches, ONE process with a `.control` loop, and ONE `.dc` sweep (the idiomatic equivalent for supply corners). ## Caveats

- The host is shared and noisy; `noisy` marks series whose spread exceeds 20 % of the median. Re-run on a quiet machine before quoting absolute times.
- Hybrid or frequency-scaling CPUs (performance and efficiency cores, turbo) make short processes bimodal: the same ngspice launch can take 30 ms or 60 ms depending on the core it lands on. Series are interleaved and repeated so both sides see the same mix, but the medians still carry that spread; `--pin-cpu N` pins the sequential children to one core for steadier numbers (parallel workloads are never pinned).
- The like-for-like analysis ratio pairs ngspice `Total analysis time` with RustSpice `compile_us + analysis_us`: the closest comparable pair the two tools report, not an exact phase match (their phase boundaries differ; ngspice's figure includes its matrix setup, RustSpice's compile its symbolic analysis / JIT). The end-to-end ratio is the only one that needs no assumption about phase boundaries.
- RustSpice's transient is fixed-step (no local-error control, no breakpoints); ngspice's default transient is adaptive. Their errors at the same nominal step are therefore not the same quantity, which is why the accuracy columns are measured against a converged reference and the b2 step ladder shows time versus accuracy.
- The b5 / b6 ngspice multi-launch variants write their decks before timing (deck generation is not timed); the process launches themselves are.
